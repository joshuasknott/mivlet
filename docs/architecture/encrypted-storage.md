# Encrypted Local Storage & Portable Workspace Archives

The Fable desktop application initializes `fable-vault.db` in the Tauri app-data directory before registering commands. SQLite provides transactions, foreign keys, write-ahead logging (WAL) recovery, and schema versioning. This document details Fable's persistence architecture, encryption guarantees, legacy JSON migration, export/import pipeline, and operational recovery instructions.

---

## 1. Cryptographic Isolation & SQLite Vault

### Encryption Strategy
Sensitive columns (e.g., free-text fields, prompts, user drafts, run logs, credential references) are encrypted at rest using **AES-256-GCM**.
- **Fresh Nonce**: Each encrypted row uses a unique, cryptographically secure 96-bit random nonce generated by the OS.
- **Additional Authenticated Data (AAD)**: Encrypted payloads bind the table name and the stable identity columns (typically `table:{workspace_id}:{id}`) as AAD. For versioned tables (such as workflow definitions), AAD also includes the version.
- **Fail Closed**: Any payload decryption attempt where the AAD or ciphertext does not match will fail closed immediately. Swap attacks (moving a valid ciphertext to a different row or table) are blocked because AAD mismatch prevents decryption.
- **Plaintext Search Indexes**: Safe query columns (IDs, enums, timestamps, booleans, and content fingerprints) remain plaintext to allow fast indexing, foreign key constraints, and querying without decrypting payloads.

### Master Key Boundaries
The 256-bit master key is generated once on fresh installations and stored in the platform's secure credential store under `com.fable.workspace.vault`.
- If the master key is missing, malformed, or inaccessible, the application fails closed.
- The vault key is **never silently re-keyed or overwritten**, preventing accidental data loss due to corrupted keys.
- **Credential Storage Separation**: API keys and OAuth tokens are stored in the platform credential store (e.g. Keychain on macOS, Credential Manager on Windows) and never enter the SQLite database. Connector accounts in SQLite store only an opaque keyring reference (`credential_ref`).

## 2. Schema History & SQLite migrations

Schema changes are applied transactionally on startup. The schema version is recorded in `schema_meta` and reported by `encrypted_store_status`. If a database schema version is newer than the binary, the store fails closed.

- **v1**: Core data structures (projects, threads, messages, runs, tool calls, approvals, audit events, connector accounts, memory, and knowledge sources).
- **v2**: Adds search tables `connector_cache` and `connector_cache_settings` for workspace-isolated, secret-free synced connector data.
- **v3**: Adds non-secret audit columns to `audit_event` to enable action history filtering without decrypting payloads.
- **v4 (Batch 9)**: Migrates schedules and workflows from legacy JSON files into SQLite tables.

### v4 Schedules & Workflows Persistence
The automation engine persists across four workspace-isolated tables:
1. `scheduled_job`: Active automation definitions.
2. `scheduler_queue_entry`: The queue containing pending, running, or leased job occurrences.
3. `workflow_definition`: Versioned workflow step definitions.
4. `workflow_run`: History of executed workflows.

Plaintext columns (e.g., status, lease holder, deduplication key, retry count) allow the scheduler tick to query and lease jobs without decrypting. Rich contents (step details, prompts, variables, attempt results) remain sealed in the encrypted payload.

## 3. Deduplication & Execution Guarantees

Fable guarantees **no-duplicate-execution** for automated schedules and runs across restarts through three cooperating layers:
1. **Durable Queue Uniqueness**: The `scheduler_queue_entry` table enforces a database-level `UNIQUE(workspace_id, deduplication_key)` constraint. Duplicate enqueues of the same job occurrence are rejected.
2. **Lease Tokens**: Running jobs are leased to a worker. Commands updating or completing a run (e.g. `report_job_attempt`) check the matching `lease_token`. A stale worker whose lease expired cannot mutate the queue status once a new lease has been issued.
3. **Idempotency Keys**: The typescript workflow runtime utilizes the `WorkflowRun.idempotencyKey` and `workflowMutationKey` to ensure that steps are not re-executed during retries or recovery runs.

Completed queue entries remain in SQLite rather than being deleted, providing a durable history that replaces the legacy in-memory `occurrence_ledger` across restarts.

## 4. Legacy JSON Migration

On startup, Fable performs a legacy data migration for pre-v4 JSON files stored in the app-data directory.

### Migration Sources
- `scheduler-store.json` → `scheduled_job` + `scheduler_queue_entry`
- `workflow-definitions.json` → `workflow_definition`
- `workflow-runs.json` → `workflow_run`
- (Plus legacy snapshot, memory, knowledge, and connector JSONs)

### The 6-Phase Migration Pipeline (Per Source)
For each source file, migration is executed idempotently:
1. **Detect**: Verify if the JSON source file exists and is readable.
2. **Checksum**: Compute the SHA-256 hash of the file bytes.
3. **Idempotency Probe**: Query `migration_log` for the checksum. If a record with `status = 'done'` matches, skip migration.
4. **Validate & Parse**: Verify that the file content is structurally valid JSON. If malformed, record `status = 'partial'` and log the failure. It will be retried on the next application launch.
5. **Migrate Transactionally**: Upsert records inside a single SQLite transaction.
   - **Malformed Record Handling**: If a single record is malformed, it is logged and skipped, but the transaction continues so other valid records migrate.
   - **Unsupported Fields**: Any unknown legacy fields are preserved verbatim inside the encrypted payload (as `legacy_extras`), ensuring no data is silently dropped.
6. **Record Outcome**: If all records migrated cleanly, record `status = 'done'` in `migration_log`. If records were skipped or validation failed, record `status = 'partial'`, forcing a retry on the next launch (unless the source file changes).

### Rollback & Data-Loss-Prevention (DLP)
- **Transactional Rollback**: Each source file migrates in its own database transaction. Any system crash or database error rolls back the entire transaction, leaving no partial state.
- **Zero Deletion Policy**: The migration **never deletes** legacy JSON files. They remain on disk, serving as downgrade/rollback recovery targets.

## 5. Export / Import Archive Foundation

Fable supports a versioned, portable archive format (`fable.portable-workspace`) allowing users to migrate their entire workspace data.

### Export manifest (JSON)
- **Plaintext JSON**: Plaintext archive containing decrypted domain values (so the format is independent of DB internals).
- **Format Versioning**: The export uses `formatVersion: 1`, which is versioned independently from the SQLite schema version.
- **Omissions (Secret-Free Guarantee)**: To prevent accidental credential leaks, the export **deliberately excludes**:
  - API keys, OAuth tokens, and secure vault keys (keyring data).
  - The `connector_account.credential_ref` (dropped on export).
  - The `connector_cache` and `connector_cache_settings` tables.
  - Absolute local machine paths.
  - Database metadata (`schema_meta`, `migration_log`).

### The Import Pipeline
1. **Parse**: Deserialize archive JSON; reject malformed payloads.
2. **Validate**: Verify `format` header and `formatVersion`. Ensure `credentialsIncluded` is `false` (archives claiming to carry credentials are rejected). Verify referential integrity of imported records (e.g. messages link to valid threads).
3. **Plan Conflicts**: Determine inserts vs. duplicates.
4. **Apply Transactionally**: All records are written inside a single SQLite transaction. A mid-import failure rolls back the database to its exact pre-import state.
5. **Report**: Emit an `ImportReport` detailing counts of imported, skipped, and remapped records, alongside warning alerts.

### Conflict Resolution Policy
The import engine enforces a strict **skip-existing** policy. If a record ID matches a pre-existing record in the database, the import skips that record to prevent silent overwrites of local data.

### Local-First Sync Boundaries
Imported records are kept inactive to ensure local-first safety:
- **Connector Invalidation**: Imported connectors are written with `status = "disconnected"` and empty credential references. They cannot connect to external services until the user manually triggers a fresh OAuth handshake.
- **Schedule Disabling**: Imported schedules are written with `enabled = false`. They will not execute until explicitly enabled by the user.

## 6. Operational Troubleshooting & Recovery

### Supported Actions
- **Integrity Validation**: Fable runs a SQLite `integrity_check` on startup. If it fails, database startup halts to prevent compounding corruption.
- **Backup Restoration**: Backups are created via the `backup_local_data` command, which uses SQLite's `VACUUM INTO` to produce a consistent file copy (refusing to overwrite existing destinations). To restore, replace the `fable-vault.db` file while ensuring the matching OS secure master key is active.
- **WAL Set Management**: When manually copying the database for diagnostics or recovery, you **must copy the complete WAL set** (`fable-vault.db`, `fable-vault.db-wal`, and `fable-vault.db-shm`) together. Copying only the base `.db` file of an active database will corrupt the state.
- **Secure Destruction**: `delete_local_data` requires entering an explicit confirmation phrase. It deletes database rows in correct referential order, purges the connector caches, and deletes legacy JSON files, but **retains the master key** in the platform credential manager.

### Known Limitations
- **Single Workspace Stub**: Although the database schema and repository layers support multi-workspace segmentation, the desktop application frontend currently stubs commands to the `default` workspace. Workspace account switching will land in a future UI batch.
- **Opaque Credentials**: Connector credentials and vault keys are platform-specific and **cannot be exported or imported**. Re-authenticating connectors is required when importing a workspace onto a new machine.

## 7. Goal 8 Contract

Later integration should use the repository modules under `src/store/repos/` or the typed native command boundary. React must not access SQLite directly. Knowledge sources, memory, workflows, schedules, artifacts, agent runs, and the connector cache already have stable encrypted repository surfaces; Goal 8 should reconcile overlapping schemas rather than create a second database.
