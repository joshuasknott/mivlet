# Core Record Authority Matrix

**Status:** Wave 0A authority decision for Wave 0B/0C contracts and migrations

**Evidence baseline:** `48fa1effbc02c29bbce49f41db2e440ed3cb31ab`

**Date:** 10 July 2026

## Purpose

This matrix decides which system may accept the canonical mutation for each core Fable record family. It also defines the local mirror, offline, sync, conflict, credential, deletion, export, and execution-node behavior needed to implement the decision.

It is intentionally a target contract, not a description of the current schema. Current implementation evidence and the next required contract are listed separately for every family.

## Evidence and precedence

The [Product Blueprint](../product/vision.md) is the product authority; the [Master Build Plan](../product/master-build-plan.md) orders the work; [Status](../product/status.md) reports the checkout. The accepted [cloud backend ADR](../adr/2026-07-05-cloud-team-backend.md) selects Clerk + Convex, the local encrypted mirror/outbox, and the no-D1/no-credential-sync boundaries. The [encrypted-storage architecture](encrypted-storage.md), [cloud-sync design](cloud-team-sync-mvp.md), [workspace data model](workspace-data-model.md), and [cloud-sync threat note](../security/cloud-team-sync-threat-note.md) supply implementation evidence.

Two assumptions in the 4-5 July material are superseded by the 10 July blueprint and therefore must not be copied into new contracts:

- A Fable account is now required; identity is not an optional team-only add-on.
- Clerk Organizations do not define tenancy. Fable owns internal users, workspaces, memberships, invitations, roles, and authorization.

The backend and security decisions from those documents remain useful. Their optional-account, Clerk-Organization, and "solo workspace is never cloud-backed" wording requires a follow-up ADR update; this document does not silently rewrite those ADRs.

## Authority vocabulary

- **Canonical authority** is the system whose accepted record/revision decides reads, export, deletion, conflict resolution, and recovery. A cache is never canonical merely because it is newer locally.
- **Local authority** means encrypted SQLite on the owning desktop/execution node. Credentials still live outside SQLite in an OS secure store.
- **Convex authority** means a Fable-owned contract stored and authorized in Convex. Convex is an implementation of the contract, not the product ontology.
- **External authority** means Clerk or an external provider owns the upstream fact. Fable stores only a mapping, policy, or cache.
- **Node authority** is transient execution state owned by exactly one selected execution node. It must not be replicated as a second writable queue.
- **Mirror** is an encrypted, read-through copy of a Convex-authoritative record. It is replaced only by accepted revisions or tombstones.
- **Pending** is a durable local intent in the outbox. It is not teammate-visible or globally committed until Convex accepts it.

## Decided authority rules

1. **One tenancy control plane.** Convex is canonical for Fable internal users, identity mappings, workspace directory records, memberships, invitations, roles, and device enrollment in both one-member and multi-member use. This avoids changing tenancy authority when a second member is invited.
2. **Clerk authenticates; Fable authorizes.** Clerk owns sign-in/session lifecycle. A Clerk subject maps to a stable Fable internal user ID. No product foreign key uses a Clerk Organization, and domain records use internal user IDs rather than Clerk subjects.
3. **Content authority follows visibility, not workspace type.** A record is explicitly `member-private` or `workspace-shared`; there is no Personal-versus-Team workspace type. In one-member use, content defaults to local authority. In a multi-member workspace, shared-surface records use Convex authority while member-private and device-local records remain local.
4. **Membership does not upload history.** Inviting a member never uploads existing local threads, knowledge, memory, runs, artifacts, routines, or connector data. Promotion to shared authority is an explicit, auditable migration that succeeds in Convex before the local copy becomes a mirror.
5. **One writer per record.** A local-authoritative record is never also writable in Convex. A Convex-authoritative record may be edited offline only by appending a pending outbox mutation against its accepted base revision.
6. **Hard workspace and private-member isolation.** Every workspace-owned durable product record carries `workspaceId`. Private records also carry `ownerMemberId` (or a stronger private-scope identifier). Authorization filters precede retrieval, ranking, execution, subscriptions, export, and sync.
7. **No table replication.** Sync uses an explicit allowlist of Fable record contracts. SQLite tables, raw payloads, React state, connector caches, and provider responses are never generically replicated.
8. **Secrets are not records.** Clerk refresh/session credentials, provider keys, connector tokens, MCP OAuth material, device private keys, PKCE state, approval permits, browser cookies, and lease tokens never enter Convex, ordinary SQLite payloads, logs, or exports. Local secrets use the OS secure store; hosted execution needs a separate managed secret boundary.
9. **Shared state is revisioned and replay-safe.** Convex assigns a monotonic workspace revision and a record revision to every accepted shared mutation. Mutations carry an exact base revision and a stable workspace/device/client idempotency key. Tombstones beat stale writes.
10. **Execution is placed explicitly.** Product records may be Convex-authoritative while sensitive execution remains local. A run records its selected node and routing boundary. Queue, lease, permit, browser-session, and in-flight provider state belong only to that node.
11. **Derived data stays derived.** Chunks, search indexes, connector caches, previews, and shadows may be rebuilt. Sharing derived content creates an explicit shared knowledge/artifact record; it does not promote the cache itself.
12. **Export and deletion read from authority.** A solo/private export reads SQLite. A shared export reads Convex plus its authorized object store. A combined user export may include both as separate scopes. Local unlink/cache deletion is never presented as remote deletion.
13. **No competing product database.** D1, R2, Durable Objects, browser storage, and provider databases do not become parallel product authorities. R2 may hold bytes referenced by Convex metadata; Durable Objects may coordinate live sessions; neither owns the portable record contract.

## Minimum canonical contract for Wave 0B

Every shareable product record must carry or derive the following fields before another Convex table or sync allowlist entry is added:

```text
workspaceId
recordType
recordId
visibility: member-private | workspace-shared
ownerMemberId?             # required for member-private records
authority: local | convex
schemaVersion
revision                   # accepted authority revision
createdByInternalUserId
createdByDeviceId?
createdAt
updatedAt
deletedAt?
```

Shared mutations additionally require:

```text
deviceId
clientMutationId
idempotencyKey = workspaceId:deviceId:clientMutationId
baseRevision
operation
payloadSchemaVersion
payloadHash
dependsOnMutationIds[]
```

Rules for the contract:

- Convex allocates the accepted workspace revision transactionally with the record/tombstone/idempotency result.
- Mutable records reject a stale `baseRevision` unless that record type explicitly declares a deterministic field merge. No declaration means no merge.
- Append-only records use stable creator-generated IDs and idempotent create. Message edits, audit corrections, artifact revisions, and plan revisions are new immutable records or versions.
- A rejected mutation remains a local conflict/repair copy. Dependent outbox mutations stop until the parent is accepted, replaced, or discarded.
- Pull apply is one SQLite transaction: records, tombstones, shadows, link revision, and cursor advance succeed together.
- Authorization derives internal user -> membership -> role/policy -> record visibility before any record query, retrieval, or mutation.

## Migration sequence

### Wave 0B - contracts before data movement

1. Define stable IDs and TS/Rust parity for internal user, workspace, membership, invitation, device/node, visibility, authority, Connection, ProviderRoute, CapabilityGrant, Mission/Plan/Worker, RunEvent, ArtifactVersion, Routine/Trigger, and tombstone envelopes.
2. Define field-level share allowlists and redaction tests for each record family. The default is denied.
3. Define shared export/import, retention, erasure, revision, idempotency-result retention, and tombstone retention before enabling more shared writes.
4. Define the execution-driver boundary so a product record, selected execution node, and node-only queue/permit state cannot be confused.
5. Record the supersession of optional-account and Clerk-Organization tenancy assumptions in the appropriate ADR task.

### Wave 0C - tenancy, schema, and safe cutover

1. **Land the control plane first.** Add Fable internal users, identity mappings, workspace records, memberships, invitations, and account devices in Convex. Authorize with internal IDs and Fable membership; remove `clerkOrgId` as a tenancy requirement only after equivalent tests pass.
2. **Upgrade local isolation.** Add direct workspace ownership to threads, messages, runs, approvals, audit, artifacts, drafts, provider routes, Connections, and all new records. Make project optional for standalone threads. Use composite ownership constraints or guarded globally unique IDs consistently.
3. **Backfill without uploading content.** Map the local `default` workspace to the accepted Fable workspace ID, rebind/reseal AAD transactionally, and retain a recovery mapping. Existing local content remains `member-private`/local authority.
4. **Introduce accepted mirrors.** Add local membership/device caches and the canonical record envelope. Keep the current project-only cloud path disabled for product use until it speaks the new internal-user/no-org contract.
5. **Promote one family at a time.** For an explicit local-to-shared promotion: freeze that record's edits; submit an idempotent import mutation; wait for Convex acceptance/revision; write shadow + authority marker transactionally; then reopen the local row as a mirror. Failure leaves the original local authority unchanged.
6. **Never dual-write during cutover.** New writes go to exactly one adapter selected by the persisted authority marker. Compatibility reads may fall back during migration, but a fallback store cannot accept mutations.
7. **Apply deletes before updates.** Migrate local tombstones and accepted shared tombstones before enabling outbox flush for that family. Pull/restore/import must consult tombstones first.
8. **Keep queue placement local until hosted execution is explicit.** Do not sync `scheduler_queue_entry`, lease tokens, occurrence ledgers, or permits. A shared routine becomes active only after its definition is accepted and one execution placement owns its queue.
9. **Update portable archives.** Export the Fable domain envelope, not SQLite layout. Shared exports come from Convex; local exports come from SQLite; imported Connections are disconnected and routines paused; sync machinery and credentials remain excluded.
10. **Remove legacy paths last.** Delete old snapshot/document/table paths only after parity tests, isolation tests, export round-trips, rollback recovery, and the minimum existing product pass against the new contracts.

## Highest-risk authority decisions

- **Convex owns the account/workspace control plane even for one member.** This follows the blueprint's required account, Fable-owned tenancy, automatic initial workspace, and single workspace model. It deliberately differs from the older optional-cloud ADR's SQLite-only solo tenancy assumption.
- **A multi-member workspace does not make all of its data cloud-authoritative.** Visibility is explicit; private member context and device-local execution remain local. This prevents an invitation from becoming an implicit data upload.
- **Shared approvals split decision authority from execution authority.** Convex may own a shared approval decision, but only the selected node can mint and consume the exact permit. Replaying a decision cannot replay a side effect.
- **Queues and leases belong to one execution node, not to sync.** Realtime status may be shared, but copying the queue creates duplicate-execution authority.
- **Connector cache never becomes shared state.** Selected content is promoted into knowledge/artifacts under a new authority contract; raw cache/provider data and credentials stay local.

## Unresolved questions

These choices are not settled by current evidence and must be decided before their dependent Wave 0B/0C contract ships:

1. What offline grace period and reauthentication policy applies to a required Fable account, and which local actions remain available after server-side account or membership revocation is known?
2. Should `member-private` records ever sync privately across a user's devices through Convex with member-only ACLs, or remain device-local until a separate private-sync design exists? This matrix defaults them to local authority.
3. What retention periods apply to shared tombstones, idempotency results, invitations, audit actor references, run events, and deleted object bytes? What active-device watermark is sufficient for safe purge?
4. Which shared approval and audit fields are visible to owners/admins/editors, and which full details must remain only on the execution node?
5. What size/type threshold selects Convex file storage versus R2, and what atomic upload/finalization protocol prevents dangling artifact metadata or orphaned bytes?
6. What managed credential store and execution-driver lease implementation will the first hosted node use? Convex may coordinate the first hosted driver, but no hosted secret may be stored in ordinary Convex records.
7. How are cross-workspace transfers represented: copy with new authority/IDs and explicit provenance, or move with a transfer tombstone? Nothing may silently retain source-workspace authority.
8. What is the exact default visibility when a user creates a record from a multi-member workspace's general composer? The UI must make the chosen shared/private surface clear, while existing local history must never auto-promote.
