# Fable Status

Last audited: 2026-07-11.

This is the factual state of the repo, not the product pitch. Claims below were checked against current files in this checkout.

> **Document boundary:** [Product Blueprint](vision.md) defines the approved final state. [Master Build Plan](master-build-plan.md) is the ordered execution tracker. This file reports current implementation facts only.

> **Approved workspace direction:** Fable requires a Clerk-backed account, but Clerk supplies identity/session only. Fable owns internal users, workspaces, memberships, and authorization. One workspace model supports one or many members; there is no separate Personal Home, Team Workspace type, Fable Organization layer, or Clerk Organization tenancy. The implementation remains configuration-gated until live Clerk and Convex validation is performed.

## Repo Shape

- The repo is a private pnpm monorepo named `fable`, with apps `@fable/desktop`, `@fable/broker`, `@fable/marketing`, and `@fable/waitlist`, plus packages `@fable/connectors`, `@fable/knowledge`, and `@fable/protocol`.
- The desktop app is Tauri 2 plus React, TypeScript, and Vite.
- The Rust runtime is under `apps/desktop/src-tauri`.
- Product docs already exist for thesis, roadmap, architecture, connectors, native-runtime, release notes, and threat model.
- Brand assets exist under `apps/desktop/public/brand`.

## Implemented

- Mission planning foundation (**Wave 4A partial; no product journey yet**): the portable mission planner turns orchestrator-generated steps into a bounded lifecycle only after validating unique and acyclic dependencies, step/parallel/revision limits, mission worker budgets, required deliverables, and required acceptance criteria. It dynamically distinguishes delegated from genuinely parallel multi-worker plans, refuses silent depth changes, selects one immutable initial revision, and replaces it with optimistic concurrency and explicit supersession. Encrypted SQLite schema v24 atomically stores the member-private mission, selected plan, and immutable revision with owner-bound encryption; focused native coverage proves ciphertext-at-rest, member isolation, rollback on invalid/stale revision, and recovery after closing and reopening the database. Authenticated native create/read/revise commands derive workspace, member, actor, local authority, lifecycle, timestamps, and revisions from the active account context, independently repeat plan-shape, size, topology, and required-outcome validation, and expose no caller-selected scope. This is repository infrastructure, not a claimed usable mission feature: production execution events, evaluation, desktop integration, and inspectable UI remain open.
- Mission worker foundation (**Wave 4A partial; execution wiring open**): a selected generated-plan step can be compiled into a scope-matched worker with only mission-declared context, an exact named tool set, the tightest default/mission/step/request budget, explicit outputs and stop conditions, and exactly one supplied grant reference per required capability. The portable local driver runs the bounded worker through the existing provider-neutral `AgentBackend`, supplies exact tool schemas, clamps output/turn/tool limits, enforces duration and observed token ceilings, cancels at the backend boundary on overrun, and preserves partial streamed work and retryable failure truth. Authenticated native worker creation now reloads the selected persisted mission, revision, and step; requires durable dependency completion; enforces unique worker/step assignment plus separate lifetime and active-concurrency bounds; derives actor, scope, role, output contract, stop conditions, and tighter numeric/monetary budgets; and persists the revision-fenced `worker-created` event. Renderer-selected context is limited to mission-declared references and always stamped `untrusted`. The renderer cannot name tools: the current native binding maps only registered connected-source read capabilities to `connection-read`, requires each exact active read grant in the authenticated workspace/project scope, and fails closed for capabilities without a binding. Authenticated start rechecks the selected assignment and active read grants, atomically transitions an eligible run to `running` when needed, and appends one native-built first-only `worker-started` event with no observable intermediate state. A deliberately narrow OpenAI-native path can now complete an already-started worker only when it has no tools, context, capabilities, grants, or expected outputs: Rust binds the exact objective-only request to the current journal head before egress, observes a clean provider `stop`, rechecks account/workspace authority after the await, and appends an empty-output `worker-completed` event idempotently. This is terminal lifecycle evidence, not semantic output evidence. Tool-bearing workers, durable output receipts and provenance, other providers/runtimes, failure events, live grant consumption, handoffs, desktop integration, and a user-visible mission journey remain open.
- Mission run journal (**Wave 4A partial; general execution-event wiring open**): the portable reducer accepts only a sequence-one `run-created`, contiguous previous-event links, non-terminal generic transitions, dedicated legal terminal events, one exact cancellation request, exact idempotent replays, checkpoint boundaries tied to an earlier durable event, advancing recovery attempts, matching cancellation resolution, and no events after terminal state. Encrypted SQLite schema v25 stores the owner-qualified current projection and immutable event chain with separate authenticated encryption bindings. Schema v26 adds encrypted owner-qualified checkpoint state linked to its exact immutable event. Authenticated checkpoint creation derives completed workers and plan steps, committed effects, active work, and waits only from the durable journal, stores only that closed portable shape, and hashes an envelope bound to the run, event, attempt, and reference. Restore selects by journal sequence, advances exactly one attempt, and exact replay remains pinned to its original checkpoint after later checkpoints. Focused native coverage proves exact replay, changed-key rejection, stale-append rollback, member isolation, ciphertext-at-rest, event/state binding, and recovery after closing and reopening the database; migrations create no inferred runs or execution authority. Authenticated native commands create a root run only from the member's ready and currently selected persisted mission plan, read only that owner's journal, append a native-built idempotent cooperative cancellation, create/restore checkpoints while deriving workspace, member, actor, status, sequence, and timestamps, and persist the narrow empty-output OpenAI completion described above. General production worker events, semantic output receipts, and desktop recovery remain open; no desktop journey is claimed.
- Mission result evaluation (**Wave 4A partial; trusted evaluator wiring open**): the portable completion boundary turns a bounded local-worker outcome into a provider-neutral run result but does not treat backend completion as proof of mission success. Outputs must be unique declared deliverables; evaluations must target the exact worker or run; human and worker criteria require their corresponding identified reviewer; unsupported external attestation fails closed; required evidence remains visible; and bounded usage/cost is retained. Success requires the completed execution, every required deliverable and criterion, the configured minimum, and any required human acceptance. Useful incomplete work becomes an explicit recoverable partial outcome with remaining work and a next-action recommendation. This aggregation is not native evaluation authority; trusted evaluator execution, production terminal-event persistence, and product UI remain open.

- The MCP 2025-11-25 client core implements lifecycle negotiation, bounded JSON-RPC framing, paginated tool/resource discovery, timeouts and cancellation, and an exact-call authorization seam. Schema v22 provides encrypted, authenticated, member-private machine-local server configuration with secret-safe projections and revision fencing. After initialization, an optional native GET/SSE listener treats `405` as unsupported, retries transient closure, and keeps bounded event ID and retry state in Rust for `Last-Event-ID` resumption; long-lived partial-stream behavior still needs live interoperability evidence. On `401`, the native boundary can parse a bounded leading Bearer challenge, use its validated public-HTTPS protected-resource metadata URL, give its bounded scopes precedence for the exact account/workspace/configuration, or follow the standard well-known fallback order. Both generic renderer routes are control-plane-only. A dedicated exact tool path now accepts local or remote sessions, binds transport into the immutable proposal, requires fresh discovery in that exact newly opened session, explicit enablement, the exact live Connection revision, a fresh one-time approval, and a 60-second single-use permit. Rust correlates every non-empty persisted inventory to the exact bounded paginated responses it observed, rejects forged inventories or mismatched cursors, fences the discovery transaction against concurrent change, and revokes session freshness on tool/resource `list_changed`; saved discovery and enablement therefore cannot by themselves authorize a changed process or remote session. Approval metadata includes only the proposal fingerprint, bounded safe argument field paths, and bounded HTTP(S) destination origins; it excludes argument values, URL paths, query strings, bodies, and credentials. Rust constructs every call; remote POST is serialized and must return the exact correlated response; completion/failure audit remains content-free. Advanced Providers settings can prepare, approve, save, list, and discovery-check either transport while enabling nothing, with browser preview truthfully unavailable. Remote initialize failures cannot activate protocol headers or retain server session ids.

## Not Implemented Yet

- No deployed production auth broker or externally validated OAuth session. The
  repository implementation includes encrypted, atomic, one-time Durable Object
  SQLite storage behind `FABLE_BROKER_STORAGE_BACKEND=durable`, with declared
  staging/production bindings and migration metadata. Deployment, live Durable
  Object migration, and provisioning `FABLE_BROKER_STORE_ENCRYPTION_KEY` remain
  external configuration work; the local-development default remains memory storage.
- No provider-console apps, deployed callback URLs, OAuth consent verification, or non-production live OAuth validation evidence in the repo.
- No externally validated live connector sessions in this checkout. Google public-client connectors still require provider configuration and test accounts; confidential-client connectors still require the auth broker (implemented in `apps/broker` targeting Cloudflare Workers, but not yet deployed in production).
- Browser-only preview state still uses localStorage; the Tauri production path uses encrypted SQLite for main documents, schedules, workflows, and knowledge structures. Backend and connector credentials remain separately handled by OS secure storage.
- No bundled local model runtime, model download flow, model license UI, or live Ollama smoke evidence in the default suite. Ollama remains a user-installed trusted loopback integration.
- No production Clerk/Convex configuration or externally validated live Fable account session exists in this checkout. The first multi-member membership and shared-project sync slice is implemented and tested repo-locally, but its deployed two-account, realtime UI, and restart journey is not validated.
- No signed release, updater channel, macOS packaging, or Linux packaging. Release docs identify the Windows preview build path and unsigned distribution gaps.
- No product website, legal pages, downloads page, or public release pipeline in the audited files.

## Highest-Risk Gaps

- External connectors look close in the UI but remain gated by provider setup and credentials. GitHub now has a brokered live read path in code, but product messaging must keep production deployment and read-only limits clear.
- Local model execution now exists through Ollama but depends on a user-managed local service and model installation; Fable must keep avoiding bundled downloads or broader egress until those are intentionally designed.
- Mandatory Clerk identity remains separate from connector OAuth and provider credentials. Production cloud use is blocked on real Clerk/Convex configuration and live end-to-end validation, not on additional client-side account gating.
- Backup restoration requires the database and matching OS-secure master key; external recovery UI polish remains future work.
- Scheduled work still depends on a connected runnable backend and user approval gates for consequential actions; live account coverage was not externally validated in this checkout.
